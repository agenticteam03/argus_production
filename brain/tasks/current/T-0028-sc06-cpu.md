## Goal (plain language)

A container whose work needs more CPU than its limit gives is slowed down by the kernel: it is *throttled* at its
quota. RB-006 keeps this apart from a busy host, because it happens even when the host is quiet. SC-06 runs a busy
loop under a 0.3-core quota on vm-166; Argus must detect the throttling from cAdvisor's counters, open a
`cpu_saturation` incident on that container, read its CPU limit and usage, and name it as the cause.

## Decisions (2026-10-09, `conantkd` + agent)

- **Only the container trigger** (RB-006: "sustained container throttling with impact even when host utilization is
  low"). The busy-host trigger needs a host incident's scope to reach every container of the host (the open question
  in NEXT_STEP), an ACR: not this task.
- Signal `container_cpu_throttled_ratio_5m`: the 5-minute minimum of throttled CFS periods / periods (cAdvisor; no
  value without a quota), **and** `container_cpu_quota_used_ratio_5m` (usage / (quota / period)). The class matches at
  throttled **≥ 0.5 and quota used ≥ 0.8** (calibrated on vm-166: the throttled share alone counts only the periods a
  container ran in, so a bursty container far below its quota showed 0.61). Rates over **3m**: cAdvisor's samples are
  35–53 s apart.
- Alert `ContainerCpuThrottled` (same ratio, `for: 5m`), only for `argus-*` containers (never another deployment's),
  with `container` copied from cAdvisor's `name` label so the intake finds the target.
- The read gateway reports `cpu_limit_cores` (NanoCpus or CFS quota/period; unknown when unlimited), so a diagnosis
  can name the quota from evidence; the baseline concludes only when usage is ≥ 80 % of that limit, else escalates.
- Lab: `argus-lab-burner` (profile `sc06`): `cpus: 0.3`, 32 MiB, no network, `pids_limit: 8`, stops by itself after
  20 minutes.
